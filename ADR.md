# Architecture Decision Record

**Progetto:** openvehicle-data
**Data:** 2026-09-18
**Autore:** Mirko Bechini

## Decisione

Database open source di marchi, modelli, varianti e specifiche tecniche di autovetture, a partire dal mercato italiano. Dati esposti tramite dataset versionato (CSV/JSON/Parquet/SQLite), API REST di sola lettura e server MCP online, in modo che app, agenti AI e software di gestione flotte possano consultarli. Ogni dato è aggiornato e verificato: ogni campo riporta fonte, licenza, data di ultima verifica e stato di verifica.

## Contesto

Non esiste un catalogo aperto e affidabile di marchi e modelli con specifiche tecniche per il mercato italiano. Nasce dall'esperienza con un progetto di gestione flotta, che non ne ha una fonte. Pubblico: chiunque (app, agenti, sviluppatori, analisti). Gratuito e open source ora; un livello a pagamento è possibile in futuro ma non è in questa fase.

## Piattaforme scelte

- Frontend: nessuno (solo API, server MCP e dataset)
- Backend: Python 3.12+, FastAPI (con uvicorn come server ASGI), Pydantic, SDK MCP ufficiale Python; httpx e pandas per l'import, Playwright solo per siti brand che richiedono JavaScript
- Database: SQLite (master, sola lettura in produzione) + export Parquet/JSON; accesso con il modulo standard `sqlite3`, senza ORM
- Deploy: API e server MCP su Render (un solo servizio), indirizzo `onrender.com` del servizio per API e MCP; dominio proprio `openvehicle.mirkobechini.com` su Cloudflare rimandato; dataset su GitHub Releases; refresh pianificato con GitHub Actions
- Repository: git dedicato (`main` + `dev`, come da AGENT_FLOW.md), separato dal repository padre AI_developed
- Test: pytest + coverage (100% obbligatorio)

## Componenti principali

Struttura del repository: `core/` (modelli Pydantic e storage, condivisi), `pipeline/` (batch offline: importer, validazione, verifica, export; non viene deployata) e `service/` (API FastAPI + server MCP: il microservizio deployato su Render, che legge il dataset prodotto dalla pipeline).

- **Schema/modelli**: Pydantic; marchio → modello → generazione → variante → motore, con ID stabili e alias, categoria e anni di validità.
- **Storage**: unico modulo di accesso al database, per poter passare a Postgres senza toccare le API.
- **Importer**: uno per fonte (EEA CO₂, Wikidata, cardata.wiki, siti dei marchi), ognuno con provenienza e licenza.
- **Validazione/qualità**: controlli di range, unità, duplicati e conflitti tra fonti prima della pubblicazione.
- **Verifica**: stato per campo (fonte singola vs confermato da due fonti indipendenti) e `last_verified`.
- **Pipeline di refresh**: re-import pianificato, rilevamento cambiamenti e changelog tra versioni del dataset.
- **Identificativi italiani**: riferimenti al mercato italiano (es. numeri di omologazione) e ricerca per marchio/modello/motore.
- **API REST**: sola lettura, ricerca e filtri, documentazione OpenAPI automatica.
- **Server MCP**: trasporto Streamable HTTP, pubblico e in sola lettura, sugli stessi dati delle API.
- **Export dataset**: file statici versionati con changelog.

## Decisioni architetturali

- **Prima versione (v0.1) solo con fonti aperte a licenza chiara**: EEA CO₂ (CC BY 4.0, verificata il 2026-09-19 sulla scheda metadati del dataset), Wikidata (CC0) e RDW (CC0, riscontro). Ordine di sviluppo: EEA per primo, perché elenca ciò che è davvero venduto in Italia; Wikidata dopo, solo come arricchimento (ID di riferimento e alias), perché i test su dati reali l'hanno mostrata troppo frammentaria come scheletro del catalogo (per Fiat: 372 "car model", solo 7 con serie collegata, 25 con anno di inizio; modelli Lancia, Maserati e Alfa Romeo elencati sotto Fiat come costruttore storico). Rimandati a versioni successive, dopo permessi e parere legale: scraping dei siti dei marchi, cardata.wiki, dataset MIT e contributi degli utenti. Limiti noti: niente allestimenti/equipaggiamenti; passo e carreggiata solo per i veicoli immatricolati nel 2019-2022 (dal 2023 l'EEA non li riporta); nomi di marchi e modelli come dichiarati dall'EEA (in maiuscolo); auto meno recenti assenti.
- **Importer EEA** (`pipeline/importers/eea.py`): usa l'endpoint SQL REST dell'EEA con aggregazione lato server (la fonte ha una riga per auto immatricolata, circa 1,5 milioni per l'Italia nel 2025 provvisorio; i gruppi sono circa 27.800; OFFSET/FETCH è bloccato, non serve paginare). Solo categoria M1 (`Ct` e `Cr`): i furgoni N1 sono esclusi. Una variante è identificata da marchio, modello e tipo/variante/versione di omologazione; se le righe di una stessa versione dichiarano motori diversi, vince la configurazione con più immatricolazioni e le altre righe vengono contate come conflitti. Per i valori misurati (massa, CO₂) si usa la combinazione più frequente; valori fuori range diventano `None` e sono contati, senza interrompere l'import. Ogni modello ha una sola generazione "observed" con gli anni osservati nei dati: sono anni di immatricolazione, non di produzione, e verranno estesi o sostituiti da fonti migliori. Il nome del marchio in testa al nome del modello (`FIAT PANDA` accanto a `PANDA`: 177 nomi su 1.220 nei dati reali) viene tolto anche per marchi di più parole (`ALFA ROMEO`) o con trattino (`MERCEDES-BENZ`), purché resti almeno una parola: i modelli che diventano uguali si fondono, il nome è la forma pulita e le altre grafie, compresa quella con il marchio, restano alias, così la ricerca le trova ancora; gli id delle varianti usano il nome pulito. L'ordine delle parole e i nomi diversi (`PUNTO` / `GRANDE PUNTO`) non si toccano in automatico: i casi noti si correggono a mano (`merge_models`), il resto richiede un elenco di modelli o regole per famiglia. Il problema è emerso provando il server MCP su Fiat. Su dati reali (Italia, 2025 provvisorio): 91 marchi, 1.193 modelli, 12.663 varianti, validazione senza errori né warning.
- **Un solo repository, con pipeline e servizio separati**: il prodotto principale è il dataset, il servizio è un livello sottile di sola lettura; `core/` condiviso evita duplicazione dei modelli. Alternativa scartata: cartella `microservizi/`, riservata a servizi a scopo singolo.
- **Prodotto dati con API, non app**: alternativa app dedicata → scelta dataset + API + MCP, perché il valore sta nei dati e va consumato da più client.
- **Open source ora, pagamento eventuale poi**: alternativa a pagamento subito → scelta gratuito, per adozione e fiducia. Dataset con licenza aperta; API predisposta a chiavi e rate limit in futuro, senza implementarli ora.
- **SQLite invece di Postgres**: dataset piccolo e in sola lettura, zero server da gestire, clonabile dai contributori. Accesso al database isolato in un modulo per poter cambiare in seguito.
- **ID stabili: generati una volta dalla chiave naturale, poi persistiti**: formato `prefisso_slug` (`brand_fiat`, `model_fiat-500`, `gen_...`, `eng_...`, `var_...`) prodotto da `make_id`. Dopo la pubblicazione un ID non si ricalcola mai: un nome corretto o rinominato diventa un alias, non un nuovo ID. Alternativa scartata: hash del nome, illeggibile e comunque instabile se il nome cambia.
- **`sqlite3` standard invece di SQLAlchemy**: schema piccolo, nessuna dipendenza in più, e l'accesso è comunque isolato in `core/storage.py` (`Store`, con `put`/`get`/`find` generici sui modelli Pydantic e apertura `ro=True` per il servizio). Un ORM avrebbe senso solo passando a Postgres, quando la migrazione dello storage andrà rivalutata. Le chiavi esterne sono attive, quindi una variante senza generazione o motore viene rifiutata.
- **Export statici come canale primario**: gli utenti possono usare i dati senza dipendere dall'API.
- **Formato dell'export** (`pipeline/export.py`): l'export parte solo se la validazione non trova errori e, in caso di `BuildError`, non scrive nessun file. Produce `openvehicle-data.db` (copia SQLite completa), un CSV per tabella (`id` come prima colonna, alias uniti con `|`; `provenance.csv` con una riga per prova), `dataset.json`, `LICENSE-DATA`, `NOTICE`, `manifest.json` (versione `X.Y.Z`, data, conteggi, warning, SHA-256 di ogni file, versione precedente), `changelog.json` e `CHANGELOG.md`. Il changelog confronta con la cartella dell'export precedente (id aggiunti, rimossi e modificati per tabella); `last_verified` e la data di recupero non contano come modifica, altrimenti ogni refresh segnerebbe tutto come cambiato. La cartella precedente viene letta prima di scrivere, quindi si può riesportare nella stessa cartella. Il confronto funziona anche con una release costruita prima che esistessero certe tabelle (`Store.has` dice se la tabella c'è): una tabella mancante conta come vuota, così le voci nuove risultano «aggiunte»; l'ha scoperto la release 0.5.0, il cui database precedente non aveva le famiglie. Parquet è rimandato: richiede `pyarrow`, che non è ancora stato approvato. Sui dati reali (Italia 2025 provvisorio) l'export pesa circa 31 MB.
- **API REST** (`service/app.py`): `create_app(db)` è una factory (`uvicorn --factory service.app:create_app`), il file SQLite viene da argomento o da `OVD_DB` e se manca l'avvio fallisce subito. Solo GET sotto `/api/v1` (`health`, `meta`, `brands`, `models`, `generations`, `engines`, `variants`, `sources`, `search`, dettaglio per id), risposte paginate `{total, limit, offset, items}` con `limit` 1-200, filtri per `brand_id`, `model_id`, `generation_id`, `engine_id`, `fuel` e ricerca `q` su nome e alias; il dettaglio di una variante include il motore e tutta la provenienza. CORS aperto in sola lettura; nessuna autenticazione né rate limit (li gestisce Cloudflare). Viene aperto un `Store` in sola lettura per ogni richiesta, perché una connessione SQLite non si condivide tra i thread di FastAPI e aprirla costa microsecondi; su dati reali le risposte impiegano pochi millisecondi. Limiti noti: nessun filtro per anno (oggi c'è solo il 2025 osservato); la ricerca `LIKE` non ignora gli accenti e cerca solo nel nome, quindi "tesla model 3" non trova nulla mentre "model 3" sì; restano alcuni quasi-doppioni con parole in ordine diverso finché non c'è la normalizzazione dei nomi con Wikidata o per famiglia. Avvertenza sulle dipendenze: il client di test di Starlette segnala che il supporto a `httpx` è deprecato a favore di `httpx2`; da rivalutare con un aggiornamento di FastAPI.
- **Metadati di paginazione**: ogni lista paginata (REST e MCP) restituisce `total`, `count` (voci di questa pagina), `has_more` e `next_offset` (`null` all'ultima pagina; oltre il totale `count` è 0). Nasce dal test di un utente: un agente LLM ha contato male liste lunghe (40 invece di 46 modelli) anche se il servizio restituiva tutto, e con `limit` massimo 100 Mercedes (161 modelli) richiede più pagine senza che nulla lo dicesse. Le istruzioni del server MCP dicono di non contare a mano e di passare `next_offset` come `offset`.
- **Filtro per marchio sulle varianti** (`brand_id` su `GET /api/v1/variants` e sul tool MCP `list_variants`): il test di un utente sui Tesla ha mostrato che per avere le varianti di un marchio serviva una chiamata per modello, perché i nomi delle varianti sono codici di omologazione senza marchio e `q` cerca solo lì. Il filtro si risolve passando da modelli e generazioni e si combina con gli altri per intersezione (mai unione). Sui dati reali una sola chiamata restituisce le 42 varianti elettriche Tesla.
- **Id inesistenti e refusi**: il test di un utente con input sbagliati ha mostrato che `brand_id=brand_ferrarri` dava `total: 0` senza errore (un refuso sembrava un marchio vero senza modelli) e che la ricerca non tollerava i refusi. Ora un id inesistente nei filtri `brand_id`, `model_id`, `generation_id` e `engine_id` è un errore (404 nell'API REST, `ToolError` nei tool MCP) e lo stesso vale per i dettagli per id; il messaggio dice cosa manca e, se c'è qualcosa di simile, `Did you mean: ...` con al massimo 3 id (confronto senza maiuscole, `difflib` della libreria standard, soglia 0,75). La ricerca restituisce `did_you_mean` (fino a 5 nomi di marchi, modelli o alias, soglia 0,7) solo quando non trova nulla. I suggerimenti si calcolano solo sul percorso d'errore e su tutte le 12.649 varianti costano al massimo circa 40 ms; `Store.ids` legge solo gli id. Un filtro valido senza risultati resta una lista vuota. Conseguenza voluta: chi usava un id inesistente come filtro aspettandosi una lista vuota ora riceve un errore.
- **Server MCP** (`service/mcp_server.py`, SDK ufficiale `mcp` 2.x, dove `FastMCP` si chiama `MCPServer`): sette tool di sola lettura (`list_brands`, `list_families`, `list_models`, `list_variants`, `get_variant`, `search_catalog`, `dataset_info`), tutti annotati `readOnlyHint`, con schema di output, limiti sui parametri (`limit` 1-100) e istruzioni che dicono all'agente di trattare nomi e codici come dati e di citare l'attribuzione CC BY 4.0. Un id inesistente restituisce un errore con il motivo (`ToolError`), non un messaggio generico. Le query e gli schemi sono in `service/queries.py`, condivisi con l'API REST, così i due canali non possono divergere. Il server è montato nella stessa app FastAPI su `/mcp` (Streamable HTTP, stateless, risposte JSON, nessuna sessione da mantenere dietro Cloudflare e Render); il session manager dell'SDK parte nel lifespan dell'app, perché Starlette non esegue il lifespan delle sotto-app. Si instrada solo `/mcp`, senza montare l'SDK sulla radice: un mount sulla radice intercettava le richieste non riconosciute e faceva rispondere 404 invece di 405 alle scritture sull'API REST. La protezione DNS rebinding dell'SDK è disattivata in modo esplicito: serve a difendere server locali, mentre questo è pubblico, di sola lettura e senza credenziali; lasciarla attiva richiederebbe di elencare ogni host di deploy. Nessun CORS per POST: i client MCP non girano nel browser.
- **Schema di output dei tool MCP verificato come lo verifica un client**: `get_variant` restituiva anche `status` (campo calcolato) nelle voci di provenienza, ma lo schema di output dichiarato non lo elencava e vietava le proprietà extra, quindi un client con validazione rigorosa rifiutava ogni risposta con provenienza; l'ha scoperto un utente provando il servizio con un client MCP reale, mentre i test controllavano solo la validazione lato server. Lo schema che Pydantic genera in validazione non include i campi calcolati, per cui l'uscita della provenienza usa un modello dedicato, `ProvenanceOut`, dove `status` è un campo dichiarato (la forma della risposta non cambia). Regola: i test convalidano la risposta di ogni tool contro il suo `outputSchema` con `jsonschema`, sia in processo sia tramite l'endpoint `/mcp`, e la provenienza di una variante è provata anche con stati `confirmed` e `conflict`. `jsonschema` è dichiarata tra le dipendenze di sviluppo.
- **Testo esterno nei tool MCP**: nomi e alias arrivano da fonti esterne, quindi possono contenere testo scritto per ingannare un agente (prompt injection). Prima di rispondere, ogni `name` e alias più lungo di 100 caratteri o con caratteri non stampabili diventa `[removed]` (sui dati reali i nomi sono al massimo di 46 caratteri, nessuno viene toccato). Limite dichiarato: un testo breve e normale non viene fermato, quindi la protezione riduce il rischio senza eliminarlo. La difesa vera è che la pipeline non pubblichi nomi anomali e che i client trattino le risposte come dati; una regola di validazione sui nomi resta da aggiungere.
- **Deploy su Render** (`Dockerfile`, `render.yaml`, `DEPLOY.md`): un solo servizio web Docker serve API REST e MCP. Il database viene incorporato nell'immagine in fase di build da una release GitHub dei dati, con `ADD --checksum` (SHA-256 da `manifest.json`): un file diverso da quello atteso fa fallire il build. Alternativa scartata: scaricarlo all'avvio, perché dipenderebbe da GitHub a ogni riavvio e allungherebbe l'avvio a freddo; il costo della scelta è che un nuovo dataset richiede un nuovo deploy (bump di `DATA_URL` e `DATA_SHA256`, i default del Dockerfile). L'immagine gira come utente non root e ascolta su `$PORT` (default 10000). Il Blueprint non dichiara domini: il workspace Render dello sviluppatore aveva già 2 domini personalizzati, il massimo del piano gratuito senza metodo di pagamento, e Render ha rifiutato di aggiungerne altri (anche uno solo, dopo un primo tentativo con due nomi separati). Per ora API e MCP usano l'indirizzo `onrender.com`; il dominio proprio si aggiunge quando si libera uno slot o si registra un metodo di pagamento, e senza Cloudflare davanti non c'è rate limit finché non c'è il dominio. Il Blueprint usa `autoDeployTrigger: checksPass`, quindi Render pubblica solo a CI verde; il branch di deploy è `main`, quindi nulla va online prima della release voluta dallo sviluppatore. Il piano free spegne il servizio dopo 15 minuti e lo riaccende in circa un minuto; i client MCP usano POST, il caso più esposto a questo ritardo: per un uso reale serve il piano `starter` (o un ping periodico a `/api/v1/health`, che però consuma le ore gratuite). Verificato costruendo ed eseguendo l'immagine in locale sul dataset reale, il che ha trovato un errore: `ADD --chmod` applicava i permessi anche alla cartella `/data`, rendendola inaccessibile all'utente non root; ora la cartella si crea prima. Un checksum sbagliato fa fallire il build, come previsto.
- **Conteggio delle immatricolazioni** (`registrations` su modelli e varianti): provando il server MCP sono emerse voci senza senso accanto ai modelli veri (`GOLF` sotto Fiat con 1 immatricolazione, contro le 111.903 della Panda; il 17% dei modelli ha 3 immatricolazioni o meno). Non si cancellano in automatico, perché alcuni modelli rari sono veri, ma ogni voce dice quanto pesa: per la variante è il numero di auto delle righe EEA mantenute (le righe scartate per il conflitto sul motore non contano, quindi il totale è un poco più basso dei dati grezzi), per il modello la somma delle sue varianti. È una statistica derivata dalle stesse righe, non una specifica tecnica, quindi non ha una provenienza propria per campo. `Store.find` e `count` accettano `sort` (`-registrations`) e filtri `campo__gte`; i valori mancanti finiscono in fondo e non passano il filtro. L'API REST offre `sort=registrations` e `min_registrations` su modelli e varianti (default: ordine per id); i tool MCP hanno gli stessi parametri ma il default è `registrations`, così un agente vede prima i modelli veri. Cambia lo schema del database: le letture ignorano le colonne che il modello non conosce, ma un servizio con questo codice va rilasciato insieme ai dati nuovi (0.2.0).
- **Correzioni riviste a mano** (`pipeline/importers/corrections.json`): una regola automatica del tipo «scarta i modelli con poche immatricolazioni» sarebbe sbagliata. Misurata sui dati reali, la regola più stretta (al massimo 3 immatricolazioni e lo stesso nome con almeno 100 volte più immatricolazioni sotto un altro marchio) prende 7 modelli, ma tra questi ci sono auto vere (SERES 3, CIRELLI 3) e voci che in realtà sono un altro problema, cioè marchi scritti in modi diversi (VW, `VOLKSWAGEN, VW`, VOLKSWAGEN). Per questo le correzioni sono un file piccolo e in revisione dove ogni voce ha una ragione di almeno 10 caratteri: `brands` (grafia del marchio → nome canonico; le altre grafie restano alias) ed `exclude_models` (marchio e modello scritti male nella fonte: FIAT GOLF, che è un Volkswagen, e FIAT AVENGER, che è una Jeep). L'importer le applica prima di creare gli id, confronta i marchi senza distinguere maiuscole e punteggiatura, toglie il prefisso del marchio sia nella grafia originale sia in quella canonica, usa come nome il valore canonico e non il primo in ordine alfabetico, e conta le righe escluse in `excluded`. Il file è validato al caricamento (nessuna catena di mappature, nessun auto-riferimento, nessun doppione, ragione obbligatoria) ed è incluso nel pacchetto installato. È il canale previsto per i contributi supervisionati: una pull request che aggiunge una voce con la sua ragione. Sui dati reali: marchi da 91 a 84, modelli da 1.193 a 1.179, 2 righe escluse, validazione pulita. Una terza sezione, `merge_models` (marchio, modello, nome in cui confluisce, ragione), unisce due grafie della stessa auto scoperte a mano: TOYOTA `YARIS GR` in `GR YARIS` e FIAT `500 ABARTH` in `ABARTH 500`; il nome canonico è quello di destinazione, le grafie originali restano alias, le immatricolazioni si sommano e le varianti con lo stesso codice si uniscono. La validazione vieta fusioni su se stesse, catene, doppioni e un modello sia escluso sia unito. Su dati reali: 1.177 modelli (`GR YARIS` 90 immatricolazioni, `ABARTH 500` 86). Restano da fare, con Wikidata o con regole per famiglia, gli altri quasi-doppioni e i modelli spezzati per allestimento.
- **Famiglie di modelli, parte 1: la struttura** (`Family`, `CarModel.family_id`): i «modelli» del catalogo sono i nomi commerciali dell'EEA e per alcuni marchi includono allestimento e motore (Mercedes-Benz 161 voci che sono circa 29 famiglie, BMW 175, Audi 124, le 26 voci `ID.4 PRO 210 KW` di Volkswagen sono 5 modelli; 823 dei 1.177 modelli stanno in 14 marchi). Ogni modello appartiene a una famiglia, un'entità con id `family_<marchio>-<nome>`, `brand_id`, nome, alias, `model_count` e `registrations` (somma dei suoi modelli). Il campo è opzionale sul modello, la tabella `families` è creata prima di `models` e la chiave esterna impedisce famiglie inesistenti. Senza regole la famiglia coincide col modello (una famiglia per modello): le regole per marchio arrivano nella parte 2, gli strumenti di API e MCP nella parte 3. L'export produce `families.csv`, la sezione `families` di `dataset.json` e conteggi nel manifest e nel changelog. La validazione dà errore se la famiglia è di un altro marchio o se `model_count` e `registrations` non tornano con i suoi modelli, e un avviso se un modello non ha famiglia.
- **Famiglie di modelli, parte 2: regole riviste per marchio** (`pipeline/importers/families.json`): una regola universale sarebbe sbagliata, perché ogni marchio scrive i nomi a modo suo (BMW `X1 SDRIVE18D` e `118D`, Mercedes `GLC 220 D 4MATIC` e `AMG A 35 4MATIC`, Audi `A3 SPORTBACK` e `Q5 SB`, Volkswagen `ID.4 PRO 210 KW` mentre `T CROSS` e `T-ROC` sono modelli a sé) e certi nomi che iniziano allo stesso modo sono auto diverse (Toyota `YARIS` e `YARIS CROSS`, Ford `MUSTANG` e `MUSTANG MACH-E`). Per ogni marchio elencato il file ha una `reason` (almeno 10 caratteri) e una lista ordinata di regole `pattern` → `family`: il pattern è un'espressione regolare senza distinzione di maiuscole, la famiglia è un modello con riferimenti ai gruppi (``), vince la prima regola con un risultato non vuoto, e senza corrispondenza la famiglia è il nome del modello. Un marchio senza regole tiene ogni modello come famiglia a sé, quindi l'errore possibile è sempre «troppo poco raggruppato», mai «auto diverse unite per caso». Il file è validato al caricamento (regex compilabile, riferimenti ai gruppi esistenti, marchi unici ignorando maiuscole e punteggiatura, ragione obbligatoria, campi extra vietati) ed è incluso nel pacchetto. Il marchio usato è quello canonico dopo le correzioni. Regole iniziali per 18 marchi, provate una per una sui nomi reali con un elenco delle famiglie per marchio: BMW (codice SUV o numero di serie), Mercedes-Benz (`GLC`, `A-CLASS`, `G-CLASS`, `VITO`, `SPRINTER`...), Mercedes-AMG, Audi, Porsche, Volkswagen (solo le `ID.`, `TOUAREG`, `CADDY`), Maserati, Ferrari (anche `SF 90` = `SF90`), Cupra, MINI, Lexus, Skoda, Volvo, Hyundai (`IONIQ5` = `IONIQ 5`), Renault, Opel, Bentley, Rolls-Royce. Sui dati reali: 1.177 modelli diventano 634 famiglie (BMW 175 → 30, Mercedes-Benz 161 → 26, Audi 124 → 34, Porsche 49 → 6), validazione pulita. Restano da fare, con regole o Wikidata, gli altri marchi e i casi come `500 ABARTH` e `ABARTH 500` in famiglie diverse. Le regole nuove arrivano via pull request con la loro ragione.
- **Famiglie di modelli, parte 3: API e MCP**: `GET /api/v1/families` (filtri `brand_id`, `q`, `sort`, `min_registrations`, paginazione completa) e `GET /api/v1/families/{id}`; filtro `family_id` su modelli e varianti, combinato per intersezione con gli altri; il tool MCP `list_families` (default ordinato per immatricolazioni) e il parametro `family_id` in `list_models` e `list_variants`. La ricerca restituisce anche le famiglie e i suggerimenti `did_you_mean` considerano i loro nomi; un `family_id` inesistente è un errore con «Did you mean» come per gli altri id; `meta` e `dataset_info` contano le famiglie. Le istruzioni del server MCP dicono di partire da `list_families` per i marchi che elencano un modello per motore o allestimento (BMW, Mercedes-Benz, Audi, le `ID.` di Volkswagen), così un agente vede 26 famiglie di Mercedes-Benz al posto di 161 voci. Sui dati reali: `list_families` per Mercedes-Benz dà GLC (11 modelli, 13.713), GLA, A-CLASS...; la famiglia `ID.4` di Volkswagen contiene i suoi 6 modelli; la famiglia BMW X1 ha 58 varianti.
- **Più anni dall'EEA (2019-2025)**: con il solo 2025 mancavano quasi tutti i veicoli già in circolazione in una flotta. Verifiche fatte il 2026-09-20 sul servizio dati e sui metadati: le tabelle finali esistono per 2020-2024 (`co2cars_2020Fv22`, `co2cars_2021Fv24`, `co2cars_2022Fv26`, `co2cars_2023Fv28`, `co2cars_2024Fv30`), il 2025 è provvisorio (`co2cars_2025Pv31`) e il 2019 finale è solo nella tabella combinata `co2cars` (filtro `Year=2019 AND Status='F'`); l'Italia ha circa 1,3-1,9 milioni di immatricolazioni all'anno dal 2018, mentre prima ci sono solo campioni da circa 20.000, quindi il 2010-2017 è escluso; il 2018 è escluso perché per il 70% ha solo la CO2 del vecchio ciclo NEDC e lo schema tiene solo quella WLTP. Passo e carreggiata sono presenti quasi sempre per 2019-2022 e assenti dal 2023: per i veicoli di quegli anni il buco dei dati 2025 si chiude in parte. Licenza: per tutti e sette i record di metadati (2019, 2020, 2021, 2022, 2023, 2024 finali e 2025 provvisorio) `License CC-BY 4.0`, titolare del copyright `Directorate-General for Climate Action (DG-CLIMA)` e `No limitations to public access`, letti il 2026-09-20; `NOTICE` cita DG Clima e gli anni, e `eea-co2.license_checked` è aggiornata. Il registro `pipeline/importers/eea_datasets.py` elenca per anno tabella, stato (F/P) e UUID del record; l'evidenza di ogni campo tecnico punta al record dell'anno da cui viene il valore. Regole di unione: una variante vista in più anni è una sola, con `year_from`/`year_to` uguali al primo e all'ultimo anno visto (possono esserci anni intermedi mancanti), immatricolazioni sommate su tutti gli anni, e ogni campo tecnico preso dall'anno più recente che lo ha (quindi il passo del 2022 resta per una variante venduta anche nel 2025); gli anni della generazione «observed» sono minimo e massimo delle sue varianti. Le contraddizioni sul motore si risolvono dentro ogni anno (vince la configurazione con più immatricolazioni) e l'anno più recente definisce il motore della variante. Un primo tentativo faceva votare la maggioranza su tutti gli anni insieme e scartava 32.572 righe su 196.118 (17%: i costruttori aggiornano i dati di una versione da un anno all'altro), accorciando gli anni e sottostimando le immatricolazioni; con la regola per anno le righe scartate sono 593 (0,3%). Il nuovo test con lo stesso client HTTP su più anni ha scoperto che `fetch` chiudeva un client ricevuto dall'esterno: ora chiude solo quello che crea. Il limite di plausibilità del passo sale da 4.000 a 4.500 mm (il Fiat Ducato in versione camper o minibus arriva a 4.035). Sui dati reali: sette anni in circa 21 secondi, 196.118 righe raggruppate, 48.889 varianti (erano 12.649), 99 marchi, 1.950 modelli, 1.068 famiglie, 10,3 milioni di immatricolazioni (coerente con l'Italia), 31.231 varianti con il passo (erano nessuna), database di 70 MB. `python -m pipeline.build --years 2019-2025` (anche `2025` o `2021,2023`) sostituisce `--table --year`. Limiti noti da trattare con issue separate: correzioni sui marchi e regole di famiglia scritte sui nomi del 2025, da rivedere sui nomi degli anni vecchi (99 marchi contro 84); filtro per anno nell'API.
- **Seconda fonte: RDW (Paesi Bassi)**: serve per portare i campi tecnici a `confirmed`. Verifiche del 2026-09-20: la tabella `Gekentekende_voertuigen` (`m9d7-ebf2`) e quella dei carburanti (`8ys7-d773`) hanno licenza `Public Domain` (attribuzione `Team Open Data RDW`) e `NOTICE` la cita; i dati sono una riga per targa, quindi si raggruppano sul server (`$group`, come per l'EEA) per marchio, modello, tipo, variante e versione e nessuna targa esce dal servizio RDW né entra nel database (nessun dato personale). La chiave `type`/`variant`/`uitvoering` coincide con quella EEA (`T`/`Va`/`Ve`), quindi il confronto è per variante. Primo passo: solo la tabella principale, cioè massa in ordine di marcia (`massa_rijklaar`), cilindrata (`cilinderinhoud`) e passo (`wielbasis`, in cm). CO2 e potenza stanno nella tabella carburanti, che ha solo la targa come chiave e non si raggruppa sul server: restano `single_source` finché non si trova un modo (issue separata). Misura su Fiat e Toyota (3.048 varianti nostre, query RDW su immatricolazioni dal 2019, circa 2,4 secondi): 1.143 varianti (37%) esistono anche in RDW, perché RDW contiene solo veicoli immatricolati nei Paesi Bassi; la cilindrata coincide nel 100% dei casi (1.067 su 1.067), la massa nel 98% (1.122 su 1.143; i 21 casi diversi sono contraddizioni vere, per esempio 1.120 kg contro 1.140 kg, e devono risultare `conflict`), il passo solo nell'89% (752 su 843) perché RDW lo dà in centimetri e noi in millimetri. Decisione sulla tolleranza: due valori si considerano concordi se differiscono al massimo di 1 kg per la massa e di 10 mm per il passo (arrotondamento al centimetro), esattamente per la cilindrata; l'evidenza conserva sempre il valore grezzo della fonte (il passo RDW moltiplicato per 10) e la tolleranza vale solo per calcolare lo stato, altrimenti l'arrotondamento produrrebbe falsi `conflict`. Indipendenza: EEA e RDW derivano entrambe dal certificato di omologazione del costruttore, quindi l'accordo protegge da errori di trascrizione e di aggregazione ma non è una doppia misura; l'utente ha deciso (2026-09-20) di chiamarlo comunque `confirmed` e di dichiarare qui l'origine comune. Realizzazione: `pipeline/importers/rdw.py` scarica le righe raggruppate (M1, prima immatricolazione dal primo anno importato, pagine da 50.000), per ogni chiave prende il valore più frequente di ogni campo e aggiunge una seconda evidenza `rdw-nl` ai campi che la variante ha già (mai campi nuovi); la cilindrata si verifica sul motore, e se due varianti dello stesso motore hanno cilindrata RDW diversa restano entrambe le evidenze e il campo è `conflict`. Il valore mostrato resta quello EEA. `python -m pipeline.build` lo esegue dopo l'import EEA (`--skip-rdw` lo salta). Sui dati reali 2019-2025 (circa 2 minuti e 15 secondi in più): 22.876 varianti su 48.889 (47%) trovate in RDW; massa 21.297 `confirmed` e 1.579 `conflict` (7%; differenze di solito di 20-50 kg, per esempio 1.915 contro 1.895 kg su un'Aston Martin DB12), cilindrata 875 e 20, passo 15.867 e 5. I `conflict` sono avvisi di validazione, non errori: le differenze restano visibili all'utente in `get_variant`.
- **Refresh pianificato (solo avviso)**: il workflow `.github/workflows/refresh.yml` gira il primo di ogni mese (e a mano da `workflow_dispatch`): scarica l'ultima release `data-v*`, costruisce la versione successiva (patch, `pipeline/refresh.py`) con EEA e RDW confrontandola con quella, e se il changelog ha differenze apre una issue con il changelog e conserva i file come artifact per 30 giorni; se il job fallisce apre una issue con il link all'esecuzione. Non pubblica mai una release da solo (scelta dell'utente, 2026-09-20, contro la specifica iniziale che parlava di pubblicazione automatica): pubblicare e aggiornare il pin del Dockerfile restano decisioni del developer. Permessi minimi (`contents: read`, `issues: write`), azioni fissate all'hash del commit. Il confronto ignora le date di verifica, quindi una ricostruzione con dati invariati non segnala nulla. Il workflow si può provare solo dopo il merge su `main` (i workflow pianificati e manuali si leggono dal ramo predefinito).
- **Comando di build del dataset** (`python -m pipeline.build`): importa, valida ed esporta in un solo passo, usando un database temporaneo, e non lascia file parziali in caso di errore. La pubblicazione della release resta un'azione manuale.
- **Modello di provenienza e serializzazione**: `FieldProvenance` accetta la propria forma serializzata ignorando lo `status` derivato, che viene sempre ricalcolato. Serve perché l'SDK MCP riconvalida l'output dei tool contro lo schema dichiarato.
- **Provenienza per campo**: consente di scartare una fonte problematica senza perdere il resto e di dichiarare la licenza di ogni dato.
- **Fonti**: Wikidata (scheletro e ID, CC0), EEA CO₂ (dati misurati, filtrati per l'Italia, CC BY 4.0), RDW Paesi Bassi (dati di omologazione, CC0, opzionale come riscontro), cardata.wiki (CC BY 4.0, con attribuzione, solo candidato da verificare), siti dei marchi (solo fatti: nomi di modelli, generazioni, motorizzazioni; niente testi, immagini o documenti). Prima di ogni scraping si controllano ToS e robots.txt del sito.
- **Stato di verifica derivato, mai scritto a mano**: per ogni campo lo stato si calcola dalle prove raccolte. `conflict` se le fonti riportano valori diversi; `confirmed` se almeno due fonti distinte concordano; altrimenti `single_source`. Lo stato `conflict` estende i due stati inizialmente previsti, perché il merge deve segnalare i disaccordi. Limite noto: l'indipendenza è misurata con `source_id` distinti, quindi una fonte che copia un'altra conterebbe due volte; da modellare prima di aggiungere fonti derivate (es. cardata.wiki). Una fonte è utilizzabile solo se `license_checked` è valorizzato (regola sugli importer).
- **Validazione: errori bloccanti e warning** (`pipeline/validation.py`): sono errori che fermano il build i duplicati di marchio/modello/variante (nome o alias uguali dopo normalizzazione), un campo di specifica senza provenienza, una fonte sconosciuta o con licenza non verificata e un valore salvato che nessuna prova supporta. Sono solo warning i valori fuori dall'intervallo plausibile, una cilindrata che sembra in litri, gli anni di una variante fuori dalla generazione e i conflitti tra fonti. I conflitti non bloccano perché lo stato `conflict` è già pubblicato nel dato e fermare il build a ogni disaccordo tra fonti lo renderebbe inutilizzabile. Le soglie di plausibilità sono un punto di partenza da tarare con i dati reali.
- **Playwright solo dove serve**: fallback per siti dinamici, perché pesante e fragile.
- **Licenza dati CC BY 4.0** (alternativa: ODbL): la CC BY richiede solo l'attribuzione, quindi è compatibile con le fonti in ingresso (cardata.wiki è CC BY 4.0, Wikidata è CC0), massimizza l'adozione anche da parte di aziende e non ostacola un futuro livello a pagamento. L'ODbL impone la condivisione delle modifiche allo stesso modo (share-alike): proteggerebbe da chi rivende il dataset senza contribuire, ma scoraggia l'uso commerciale e complica le fonti miste. Da riconfermare dopo la verifica della licenza EEA.
- **Licenza codice Apache-2.0** (alternativa: MIT): come MIT è permissiva, ma aggiunge una concessione esplicita di brevetti e la protezione per i contributori, utile per un progetto aperto ai contributi e con un possibile uso commerciale futuro. File separati per dati (`LICENSE-DATA`) e codice (`LICENSE`).
- **Sottodominio di primo livello** (`openvehicle.mirkobechini.com`): il certificato gratuito di Cloudflare copre solo `*.mirkobechini.com`, non i sottodomini di secondo livello (es. `mcp.api.mirkobechini.com`).
- **Python come stack**: import e pulizia dati, API e MCP condividono gli stessi modelli Pydantic in un unico linguaggio; alternativa TypeScript scartata perché l'ecosistema di elaborazione dati (pandas, Parquet) è più maturo in Python.
- **Server MCP remoto senza login**: pubblico e di sola lettura; abusi gestiti con rate limit Cloudflare. Chiavi API rimandate al livello a pagamento.
- **Contributi degli utenti (fase successiva)**: solo tramite pull request sui file dati, con controlli automatici, fonte obbligatoria e revisione del maintainer; "confermato" solo con seconda fonte. Non in v1, ma i campi di provenienza lo prevedono già.
